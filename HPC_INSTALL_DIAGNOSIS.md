# HPC install diagnosis: `OSError: [Errno 14] Bad address`

Record of three failed BindCraft2 installs on the Leipzig SC cluster (`login01.sc.uni-leipzig.de`),
working directory `/work2/hj32qadi-competition`. Written 2026-10-01.

## Summary

Three attempts to run `bash install.sh cuda12` failed on three different CPU compute nodes with
`OSError: [Errno 14] Bad address` (EFAULT) while pip was fetching/installing the NVIDIA CUDA wheels.
BindCraft2 itself never ran — the failure is in dependency installation.

| 28077299 | t005 | 00:34 | Downloading `nvidia_cudnn_cu12` (766.2 MB); connection interrupted at ~495 MB, 5 resume attempts, then EFAULT |
| 28078490 | t007 | 03:29 | Same — last started download was `nvidia_cudnn_cu12` (766.2 MB) |

## Revised reading of the traceback

**First theory (discarded): "large file on Lustre".** This does not survive testing. Controlled
write tests (`dd` at 1 M and 64 M block size, `cp`, Python 1 MiB-chunked writes, and
`shutil.copyfile`/sendfile) all wrote 600–640 MiB correctly into the same directory on both `t002`
and `paul05`. Large single-file writes are not blocked.

**Current theory: pip's concurrent batch downloader.** The call path is

```
prepare_linked_requirements_more → _complete_partial_requirements → batch_download → DownloadFn.__call__
```

`batch_download` is pip's **parallel/batched** wheel fetch (pip 26.2.1 in this venv). Several
hundred-MB wheels are therefore being written to Lustre *concurrently*, with the newer
resume-on-incomplete-download logic layered on top. The synthetic tests above were all strictly
serial single-file writes, so they would not reproduce this pattern.

Supporting detail: run 2 shows the resume path engaging five times (`Attempting to resume incomplete
download ... attempt 1..5`) with the offset barely advancing (494.9 → 496.0 MB) before EFAULT. That
is consistent with a download/write path already in a degraded state rather than a clean disk error.

Caveat: this is a hypothesis that fits the traceback better than the file-size theory. It is not
confirmed. EFAULT (bad pointer) remains an unusual errno for this path.

## Environment facts gathered

- **GPUs:** V100 (cc 7.0, 6 nodes), RTX 2080 Ti (cc 7.5, 18), A30 (cc 8.0, 12), L40S (cc 8.9, 4).
  Driver 580.178.04, reports CUDA 13.0. Compute nodes do reach pypi.org and storage.googleapis.com.
- **`cuda12` vs `cuda13`:** `pyproject.toml` states cuda13 is the stack every recorded baseline was
  measured on. cuDNN wheel is 766 MB on cu12 vs 537 MB on cu13. cuda13 requires cc ≥ 7.5, so it
  covers 34 of 40 GPU nodes, excluding only the V100s.
- **Filesystem:** `/work2` is Lustre 2.17.0. No inactive/degraded OSTs. Default layout is DoM for the
  first 128 KiB then single-stripe to 256 MiB.
- **Quotas:** block 3.725 T of 5 T (fine). **Inodes 9,864,018 of 10,000,000 (98.6%)** — only ~136k
  files free. Not believed to cause EFAULT (Lustre returns EDQUOT), but tight for a full CUDA venv
  plus campaign output.
- **User pip config:** `~/.pip/pip.conf` and `~/.config/pip/pip.conf` (autogenerated by NVIDIA
  PyIndex) add `pypi.ngc.nvidia.com` as an extra index and set `no-cache-dir = true`. Compute nodes
  cannot resolve that host, producing retry warnings. Worked around per-job with
  `PIP_CONFIG_FILE=/dev/null`; the files themselves were not edited.

## Hypotheses tested and disproved

| Hypothesis | Test | Result |
|---|---|---|
| Large file on Lustre | `dd`/`cp`/Python 600–640 MiB writes on t002, paul05 | **Disproved** — all passed |
| Bad compute node | Runs on t004, t005, t007 | **Disproved** — all three failed |
| pip 26.2.1 concurrent `batch_download` | Pinned pip 24.3.1 (job 28084756) | **Disproved** — identical failure |
| `cuda12` wheel set specifically | Installed `cuda13` (job 28084756) | **Disproved** — failed on the cu13 cuDNN wheel |
| File size threshold | cu13 run failed at **16.8 MB** | **Disproved** — far below earlier failure points |

## Root cause (established)

**Any download streamed through CPython's file-write path onto this Lustre mount fails with EFAULT.**
The same bytes written by a non-Python tool succeed.

| Writer | Implementation | Result |
|---|---|---|
| pip (4 runs, pip 24.3.1 and 26.2.1) | CPython + `tempfile` | EFAULT at 16.8 MB / 495 MB |
| `bindcraft fetch-weights` | CPython `urllib` + `open()` write loop | EFAULT at 0.9 GB |
| `dd`, `cp` | C | OK, 600+ MiB |
| `uv pip install` | Rust | **OK — full install** |
| `curl` | C | **OK — 6.4 GB** |

Failure always follows the sequence: `Connection interrupted while downloading` → resume attempts that
barely advance → EFAULT on `close()` of the temporary file. EFAULT (bad userspace pointer) remains an
unusual errno for this path; the precise interaction between CPython's buffered IO and this Lustre
client (2.17.0) was not identified and would be worth reporting to the cluster administrators.

## Resolution (2026-10-01, verified)

Installed successfully by replacing both Python downloaders:

1. **`uv pip install --python .venv/bin/python -e ".[cuda13]"`** (job 28085252) with
   `UV_CONCURRENT_DOWNLOADS=1`, `UV_HTTP_TIMEOUT=600`. Full dependency set installed;
   `selfcheck --shipped-only` clean.
2. **`curl -L --fail --retry 20 --retry-all-errors -C -`** for the AlphaFold tar, then `tar -xf`
   (job 28085441). 6.4 GB downloaded, 16 checkpoints unpacked.
3. `python -m bindcraft.selfcheck cuda13` → **SELFCHECK CLEAN**.

Final state:

- venv: `/work2/hj32qadi-competition/BindCraft2/.venv` (Python 3.12.11, jax 0.11.2, CUDA 13)
- weights: `/work2/hj32qadi-competition/bindcraft_weights/alphafold/`
- branch `ph-sensitive-loss` @ `6513f47`

## Carry forward into every campaign job

- `export BINDCRAFT_WEIGHTS=/work2/hj32qadi-competition/bindcraft_weights` — otherwise BindCraft2
  looks under `$HOME/.cache/bindcraft`.
- `export PIP_CONFIG_FILE=/dev/null` if pip is ever invoked — the user's `~/.pip/pip.conf` adds an
  unreachable NVIDIA index.
- **Use `uv` or `curl`, never Python, for any further large download into `/work2`.**
- **Submit to `gpu-a30`, `gpu-l40s` or `gpu-rtx2080ti` only.** The install is CUDA 13, requiring
  compute capability ≥ 7.5. The 6 V100 nodes (cc 7.0) cannot run it, and the generic `gpu` partition
  includes them.
- Inode quota remains tight: 98.6% used, ~136k files free.
